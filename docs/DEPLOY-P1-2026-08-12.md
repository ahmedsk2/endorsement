### The single most important fact in this document

> **Once migration `2026_08_10_120003_move_name_and_position_off_users` has run, redeploying the
> previous image is no longer a rollback — it is an outage.**

That migration DROPs `users.full_name` and `users.position`. The `8886f8d` code names both as real
columns in **fourteen** files under `app/` (`git grep -l full_name 8886f8d -- app/`), including
`app/Http/Middleware/HandleInertiaRequests.php`, which runs on *every* page.

**What that looks like was measured in the rehearsal, and it is the opposite of what this
document first said.** Running the `8886f8d` code against the upgraded schema does not produce a
site that 500s. It produces a site that is **up, healthy, and refuses everybody**:

```
$user->full_name  = NULL      <- Eloquent returns null for a missing attribute. No error.
$user->position   = NULL
/up                    200    <- the container reports healthy
/endorsement/PICU      403
/profile               403
/admin/users           403
WRITE users.full_name         QueryException: no such column
```

`$user->position` resolving to NULL means `AccessControl::resolve()`'s
`->where('role_capabilities.position', $user->position)` (`app/Support/AccessControl.php` line 147
at `8886f8d`) matches no row, so the effective capability set is empty and **every `cap:`-gated
route denies, including `/profile`**. Only a *write* naming a dropped column is a 500.

**The consequence: nothing pages you.** `/up` is a bare `DB::connection()->getPdo()` — no table,
no user — so the container HEALTHCHECK (`Dockerfile` line 196, `wget … /up`) stays green;
`endorsement-uptime-check` probes `PUBLIC_URL`, which `docs/RUNBOOK-DEPLOY.md` line 170 sets to
`https://endorse.towardpcc.com/up`, so it stays green; and `scripts/verify-live.sh` exercises only
anonymous paths (`/login`, `/forgot-password`, `/up` must be 200; guarded routes must render no app
content to a guest), all of which still hold — a guest sees `'user' => null` and the login page
renders normally. **The signal that this has happened is a clinician telephoning to say nothing
opens.** Three monitors green, everybody locked out.

The conclusion is unchanged: **do not redeploy the old image after migration #6.** But do not
expect an alert to tell you that somebody did.

So this deploy has two regimes, and you cross the line in the middle of §4:

- **Before that migration** — Coolify → Deployments → previous → Redeploy is a complete,
  lossless rollback.
- **After it** — the only recoveries are *roll forward* (fix and redeploy) or *restore the
  pre-deploy backup and redeploy `8886f8d`*, which discards every clinical write made since
  the backup. §7 is the honest version of this.

Plan the window accordingly: this is not a deploy to start at 16:00 on a Thursday.

Do all six. Steps 1–3 are what make §7 possible at all.

### 1.1 Open a shell with the right stack selected

```bash
eval "$(sudo bash docker/instance-env.sh oo7d7si62yhyi7fx10hrck6q)"
```

Exports `APP`, `DB`, `DBNAME`, `DBUSER` (verified against `docker/instance-env.sh` line 48).
It prints one line on stderr:

```
instance-env.sh: app=<container> db=<container> database=<dbname> user=<dbuser>
```

**Read it. Confirm the database name is QCH's.** It refuses (prints `unset APP DB DBNAME
DBUSER; false`, exits 1) when zero or more than one stack matches — but a UUID typo that
happens to match a *different real* stack will not refuse, and this line is the only thing that
catches that.

### 1.2 `audit:verify` GREEN, before anything else

```bash
sudo docker exec -u app "$APP" php artisan audit:verify; echo "exit=$?"
```

Expect `Audit chain intact: N rows verified.` and `exit=0` (`app/Console/Commands/AuditVerify.php`
lines 77–84 — the command takes no options and issues no writes).

**If this is not green, stop and do not deploy.** A chain break discovered *after* a 22-migration
deploy is unattributable, and the repair for a genuine break is documented as a permanent,
explained break plus an incident record — not a clean bill of health
(`docs/RUNBOOK-BACKUP.md` §4). Record the row count; you will compare it in §8.

### 1.3 Take the backup, and check it is a real one

```bash
sudo docker exec -u app "$APP" php artisan backup:run; echo "exit=$?"
sudo docker exec "$APP" ls -la storage/backups | tail -6
```

`backup:run` refuses without `BACKUP_PASSPHRASE` or `openssl`, and — since the ops-rehearsal fix —
aborts if the `audit_log` append-only triggers are not actually blocking (it inserts a throwaway
row, tries UPDATE and DELETE, and rolls back unconditionally: `app/Console/Commands/BackupRun.php`
lines 394–455). **That abort is also your answer to §6.2** — if the backup succeeds, the triggers
from `least-privilege.sql` are live.

The archive is `endorsement-<slug>-<Y-m-d_His>.sql.gz.enc` plus a `.meta.json` sidecar carrying
`slug`, `stamp`, `bytes`, `app_key_fingerprint`, `hostname`.

> **Note the slug in that filename.** If you have not yet set `INSTANCE_SLUG` (§3), this archive
> is named from `Str::slug(APP_NAME)`, not `qch`. That is expected and fine — but it means the
> pre-deploy archive and the first post-deploy archive will have **different names**, and
> `--keep`'s prune glob is anchored per slug. See §6.7.

### 1.4 Test the restore. Do not assume it.

`docs/superpowers/specs/2026-08-08-munawib-endorsement-integration-design.md` §14 item 11 is
precise about the gap: the runbook records the first drill in prose (**2026-07-25**) and carries
a per-instance register, but *"nothing machine-checks that a quarter has not passed since."* It
is now 2026-08-12 — inside the quarter, but this is a 22-migration deploy against children's
clinical records and §7's fallback is literally this archive.

The drill is `docs/RUNBOOK-BACKUP.md` §3, lines 74–216. Its load-bearing steps:

```bash
# 1. Decrypt (on the host, into a scratch location)
openssl enc -d -aes-256-cbc -pbkdf2 \
  -in endorsement-<slug>-YYYY-MM-DD_HHMMSS.sql.gz.enc | gunzip > restore.sql

# 2. Load into a SCRATCH database, as root — never the app credential, which has no DDL
mysql --ssl-verify-server-cert=0 -h db -u root -p <scratch-db> < restore.sql

# 3. Re-run docs/sql/least-privilege.sql against the restored database.
#    A least-privilege dump never carries the append-only triggers. (RUNBOOK-BACKUP.md 133-137)

# 4. Verify against the SCRATCH database, not the live one
PW=$(sudo docker exec "$DB" printenv MYSQL_ROOT_PASSWORD)
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot \
  -e "GRANT SELECT ON \`<scratch-db>\`.* TO '$DBUSER'@'%'; FLUSH PRIVILEGES;"

sudo docker exec -u app "$APP" php artisan tinker --execute="
config(['database.connections.mysql.database' => '<scratch-db>']);
Illuminate\Support\Facades\DB::purge('mysql');
echo Illuminate\Support\Facades\Artisan::call('audit:verify');
echo Illuminate\Support\Facades\Artisan::output();
"
```

Step 4's shape is not decoration: `config:cache` bakes `DB_DATABASE` in at boot, so
`docker exec -e DB_DATABASE=...` silently verifies the **live** database instead and reports a
pass that proves nothing.

Success: row counts plausible, a handover sheet opens, `audit:verify` exits 0. One expected
discrepancy — live `audit_log` will have one row more than the archive.

**Write the date into the register at the bottom of `docs/RUNBOOK-BACKUP.md`** (`qch` /
2026-07-25 / *(record here)* / *(record here)*). That table is the only record that exists.

### The three that are not routine

**#6 `move_name_and_position_off_users` — the one-way door.** Covered in §0. Take the extra dump
the standing runbook asks for before you start §4:

```bash
PW=$(sudo docker exec "$DB" printenv MYSQL_ROOT_PASSWORD)
sudo docker exec -e MYSQL_PWD="$PW" "$DB" \
  mysqldump -uroot --single-transaction --routines "$DBNAME" > pre-p1-$(date +%F).sql
```

**#17 `widen_rich_text_handover_columns` — the slow one, and it is four passes, not one.**
MySQL 8.4 refuses both `ALGORITHM=INSTANT` and `ALGORITHM=INPLACE` for `TEXT`→`MEDIUMTEXT` (the
on-disk length prefix widens, 2 bytes → 3) and falls back to `ALGORITHM=COPY`, rebuilding
`handovers` row by row. Reads continue; **writes to `handovers` block** — an endorsement save
queues rather than fails, so this presents as "the app got slow", not as an error.

Compiled against Laravel's own MySQL grammar (`Illuminate\Database\Schema\Grammars\MySqlGrammar::
compileChange()` emits one statement per column), the migration issues **four** separate
statements:

```sql
alter table `handovers` modify `disease` mediumtext null;
alter table `handovers` modify `details` mediumtext null;
alter table `handovers` modify `plan`    mediumtext null;
alter table `handovers` modify `nevent`  mediumtext null;
```

Each is its own COPY rebuild. `docs/superpowers/plans/2026-08-09-ops-rehearsal-defects.md` line
285 records *"~26 MB/s: 20,000 rows / 157 MB ≈ 6 seconds"* but does **not** say whether that
timed one statement or all four. Size it both ways from §1.6 and plan for the worse:

- optimistic (the figure was end-to-end): `table_MB / 26` seconds
- conservative (the figure was one pass): `4 × table_MB / 26` seconds

COPY is atomic per statement — either a rebuild lands or the original table is untouched — so
this is a *waiting* risk, not a data-loss risk.

**#1 `add_configuration_to_units` — `active` defaults FALSE and the backfill is code-matched.**
A `units` row whose `code` is not one of the four constants is left `active = 0` and `bar_class
IS NULL`, and stops being routable. That is deliberate (fail closed). §5.1's counter-check is what
surfaces it — `display_order` alone gives no signal, since a missed row just sorts to the end.

### Privileges

The forward run needs **`ALTER, CREATE, REFERENCES`** and nothing more. Confirmed by reading all
22 `up()` methods: none calls `dropIfExists` or `DROP TABLE`, so **`DROP` is not needed to
migrate** (it *is* needed to roll back — §7). `INDEX` is not needed; `2026_08_10_120003`'s index
drop is emitted as `alter table users drop index ...`, which `ALTER` covers.

Two caveats on the standing runbook's *"verified across the full chain"* claim: that verification
was the 2026-08-09 MySQL rehearsal, which predates migrations **#21 and #22** (added 2026-08-11).
Both are plain `Schema::create` with `constrained()` foreign keys — the identical shape the
rehearsal already proved needs `CREATE` + `REFERENCES` — so the grant is unchanged, but they
were not in the measured run.

`php artisan db:seed --force` needs **no** elevated privilege. Verified: the seeders contain no
`Schema::`, no `TRUNCATE`, no `DB::statement`, no raw SQL — only SELECT/INSERT/UPDATE and one
no-op `DELETE`. Revoke before you seed.

### 3.3 `HIJRI_OFFSET_DAYS=-1` — set it, and keep setting it

QCH's calibration, established against the department's own published calendar across a month
boundary. Without it every Hijri date renders **one day late, with no error anywhere**.

> **⚠ SET `HIJRI_OFFSET_DAYS=-1` IN COOLIFY BEFORE THIS DEPLOY — AND NEVER REMOVE IT AFTERWARDS.**
>
> **This is not a one-time convenience. It is a standing hazard from this deploy onward.**
> `db:seed --force` runs on every deploy and writes this column from the environment every time.
> If the variable is ever unset in Coolify, `docker-compose.production.yml`'s
> `HIJRI_OFFSET_DAYS: ${HIJRI_OFFSET_DAYS:-0}` supplies the literal `0` — so **an unset variable
> is not "leave it alone", it is "reset the department's calendar to 0"**.

Measured four ways in the rehearsal, each run starting from an administrator-calibrated
`hijri_offset_days = -1`:

| `HIJRI_OFFSET_DAYS` in the container | After `db:seed --force` | Reachable in production? |
|---|---|---|
| absent | **-1 — survives** | **No.** The compose file guarantees the variable is present. |
| `0` | **0 — the calibration is silently reverted** | **Yes — this is what an unset Coolify variable becomes.** |
| `-1` | -1 | Yes, and it is what you want |
| `-5` | seed **throws**, row unchanged at -1 | Yes, on a typo — and see the warning below |

The mechanism, verified in the tree: `config/endorsement.php` line 59 is
`env('HIJRI_OFFSET_DAYS')`; `ReferenceSeeder` lines 176–191 write the column whenever that value is
neither `null` nor `''`. The string `"0"` is neither.

**So there are two things to get right, not one:**

1. **For this deploy:** set `HIJRI_OFFSET_DAYS=-1` in Coolify *before* you deploy and
   `db:seed --force` applies it. No hand `UPDATE` is needed.
2. **For every deploy after this one:** `hijri_offset_days` is *also* editable at
   Admin → Structure → Calendar (bounded `[-2, 2]`, audited). An administrator who recalibrates
   there and does not also change the Coolify variable **has their change silently reverted at the
   next deploy** — no error, no log line, every Hijri label on every screen quietly wrong again.
   **The Coolify variable is the source of truth. Change both together, or not at all.**

The seeder's own docblock still claims the column is "NEVER reverted to 0 by a re-seed". That
claim is true only when the variable is *absent*, which this compose file guarantees it is not.
`docs/RUNBOOK-DEPLOY.md`'s P1a section said the same thing and has been corrected (§10 item 2).

> **THE TYPO THAT DOES MORE THAN FAIL THE SEED**
>
> An out-of-range value is refused loudly — `ReferenceSeeder` throws `InvalidArgumentException`
> outside `[-2, 2]` (`Institution::HIJRI_OFFSET_BOUNDS`) rather than corrupting the row. **But it
> throws from the LAST block of `ReferenceSeeder::run()`, and `DatabaseSeeder` calls
> `ReferenceSeeder` then `AccessControlSeeder`.** So a typo in this one variable does not just fail
> the seed step — it fails it **with the capability seed never having run**.
>
> The failure does not present as a bad date. It presents as **missing screens**: `rota.view`,
> `rota.manage`, `clinics.view`, `people.manage` and `structure.manage` would simply not exist as
> `capabilities` rows, so every new surface this release turns on 403s for everybody and the nav
> entries do not render. Somebody staring at an empty Access Control screen will not think of the
> Hijri offset.
>
> **If `db:seed --force` exits non-zero, do not walk the screens — read the exception.** The fix is
> to correct the variable and re-run `db:seed --force`; both seeders are idempotent and the second
> run applies the capabilities as if nothing had happened. Confirm with §5.4's first query
> (`SELECT COUNT(*) FROM capabilities;` must be 14) before you believe the deploy is finished.

Verify after §5:

```bash
sudo docker exec -u app "$APP" php artisan tinker \
  --execute="echo App\Models\Institution::current()->hijri_offset_days;"      # expect -1
```

Then do the real check, which is not a number: open **Admin → Structure → Calendar**, which shows
today's Gregorian and Hijri labels side by side computed exactly as every clinical screen computes
them, and compare two consecutive days across a Hijri month boundary against the department's own
published calendar.

### 3.4 What else changed in the compose file

- **`APP_TIMEZONE` became a variable** (was the literal `Asia/Riyadh`). Leave it unset in Coolify;
  the default is unchanged. `APP_TIMEZONE` must be correct before the first clinical write —

  This is the same `${VAR:-default}` shape as §3.3's, with the opposite consequence: here the
  compose default **is** the value you want, so leaving it unset is correct. §3.3 is dangerous

- **`--default-time-zone=+00:00` is new on the `db` service.** This pins MySQL's session zone,

  **Operational consequence: changing `db.command` means Docker recreates the database
  container on this deploy.** The `endorsement-db` volume persists, but expect a short database
  outage during the deploy and confirm the db healthcheck goes green before §4.

## 4. The deploy

```bash
git push origin main
```

Then **Deploy** in Coolify. The container does not migrate at boot —
`docker/entrypoint.sh` never touches the schema, so an unattended restart can never alter a
clinical database. It rebuilds config/route/view caches as `app` (not root) and refuses to start

(commit `6e21336`). It is now installed in both the vendor stage (so composer's platform check is

### 4.2 Migrate — grant, migrate, revoke

Unchanged from `docs/RUNBOOK-DEPLOY.md`, reproduced so this file is runnable on its own:

```bash
eval "$(sudo bash docker/instance-env.sh oo7d7si62yhyi7fx10hrck6q)" && \
PW=$(sudo docker exec "$DB" printenv MYSQL_ROOT_PASSWORD) && \
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "GRANT ALTER, CREATE, REFERENCES ON \`$DBNAME\`.* TO '$DBUSER'@'%'; FLUSH PRIVILEGES;" && {
  sudo docker exec -u app "$APP" php artisan migrate --force; rc=$?
  sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "REVOKE ALTER, CREATE, REFERENCES ON \`$DBNAME\`.* FROM '$DBUSER'@'%'; FLUSH PRIVILEGES;"
  echo "migrate exit=$rc"
}
```

Up to and including the `GRANT`, `&&` is load-bearing — `instance-env.sh` prints `false` on
refusal, so a refusal aborts everything. Past the `GRANT`, the brace group runs the `REVOKE`
**unconditionally**: a failed migration is exactly when elevated privileges must not linger while
you debug.

Then verify the revoke actually landed:

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "SHOW GRANTS FOR '$DBUSER'@'%';"
```

Expect `SELECT, INSERT, UPDATE, DELETE` and **none** of `ALTER`, `CREATE`, `REFERENCES`, `DROP`.

**If `migrate exit=` is non-zero, do not just re-run it.** MySQL has no transactional DDL: a
`Schema::create` with a foreign key commits the `CREATE TABLE` and can then fail on the separate
`ADD CONSTRAINT`, leaving a partially built table that is *not* recorded in `migrations`. Retrying
then produces `1050 Table already exists`, which reads like a new problem and is not. Follow
`docs/RUNBOOK-DEPLOY.md`'s five-step recovery ("If `migrate exit=` is non-zero"): `migrate:status`
names the failed migration as the first still-Pending row; read its `up()`; check for each object
it creates; drop residue as root; then retry.

**Assume this is possible for almost every one of the 22**, not just for the table-creating ones:
18 of them emit more than one statement, and only three are a single `ALTER`. §9.0's box has the
per-migration counts, and they are the map for "what might already have landed" when you read a
failed migration's `up()`. **The 2026-08-12 rehearsal cannot reassure you here at all** — SQLite
has transactional DDL, so no migration could half-apply on the engine it ran on.

### 4.3 Seed

```bash
sudo docker exec -u app "$APP" php artisan db:seed --force; echo "exit=$?"
```

Runs exactly two seeders (`DatabaseSeeder` is byte-identical to `8886f8d`): `ReferenceSeeder` and
`AccessControlSeeder`, **in that order, in one process**. `DemoSeeder` and `E2eSeeder` are not
wired in and each throws as its first statement under `APP_ENV=production` — which
`docker-compose.production.yml` pins as a literal, so the guard cannot be defeated by an unset
Coolify variable. Never call them by name.

**Check the exit code, and do not skip to §5.5's screens if it is non-zero.** The two seeders are
sequential and `ReferenceSeeder`'s last act is the `HIJRI_OFFSET_DAYS` validation, so a bad value
in that one variable aborts the run *before* `AccessControlSeeder` ever starts and the five new
capability rows are never created. §3.3's boxed warning is the whole of it: the symptom is missing
screens, not a wrong date. Both seeders are idempotent — fix the variable, run it again.

Exactly what this writes on **this already-seeded instance**:

| Table | Effect |
|---|---|
| `positions` | No change. `name` re-asserted (not dirty → no UPDATE); the `WHERE id = 1` delete is a no-op. |
| `units` | **`name` re-asserted on all four rows every run** (see §6.6). Everything else is CREATE-only. **WARD's `clinic_owner` is NOT fixed here** — migration #18 does it. |
| `institutions` | `name` preserved (CREATE-only — a rename survives, asserted by `ReferenceSeederTest`). `active` forced true. `hijri_offset_days` written from the environment (§3.3). |
| `levels` | **5 rows INSERTed for the first time** — `R1 R2 R3 R4 EXT` at `display_order` 10/20/30/40/90, `EXT.external = 1` — each stamped with `institution_id`. All fields are CREATE-only afterwards, so a later rename survives. |
| `capabilities` | **5 rows INSERTed**: `people.manage`, `structure.manage`, `rota.view`, `rota.manage`, `clinics.view`. The existing 9 are untouched (`firstOrCreate`); only a **NULL** description is ever backfilled. |
| `role_capabilities` | **13 rows INSERTed** (22 → 35). See §5.4. Nothing revoked, nothing deleted. |
| `applied_role_defaults` | **13 marker rows INSERTed** (22 → 35, or 23 → 36; §1.5). This file first said 49 → 62; the delta was right and both absolutes were wrong. |
| `cache` | The access-control generation counter is bumped once (`AccessControl::flush()`, not a global cache flush). |

No seeder ever deletes a `capabilities`, `role_capabilities`, `user_capabilities` or
`applied_role_defaults` row. The only `DELETE` in the whole seeders directory is
`Position::whereKey(1)->delete()`, and position 1 was retired long ago.

### 6.1 `rota.manage` for Chief Resident — check, but expect a no-op **on this instance**

The standing runbook says an instance that already seeded P1d-1's Chief Resident grant *keeps*
it, and must be un-ticked by hand, because `AccessControlSeeder` applies each (position,

**It does not apply here.** `git show 8886f8d:database/seeders/AccessControlSeeder.php` contains
no `rota.*`, `clinics.*`, `people.manage` or `structure.manage` key at all — the capability
`rota.manage` has never existed in this production database, so no `(5, rota.manage)` row and no
marker can exist. The grant was added in `5915bc0` and removed in `5e59904`, **both after the
deployed commit**; neither ever reached production. Current defaults give position 5
`profile.manage`, `rota.view`, `clinics.view`, `endorsement.view`, `endorsement.edit`,
`users.manage_residents` — and not `rota.manage`.

### 6.2 Confirm `least-privilege.sql` was ever applied

Its underscore-escaping bug (fixed in `416227d`, 2026-08-09) meant it could silently apply
**nothing**: MySQL stores `_` and `%` as wildcards in `mysql.db.Db`, and the official image's
auto-grant stores the database name escaped (`endorse\_live`). The old script's
`REVOKE ... ON \`endorse_live\`.*` matched no stored grant, failed with `ERROR 1141`, and aborted
the batch **before creating the triggers** — leaving the credential on `ALL PRIVILEGES` and no
append-only protection, while looking like it had run.

Three checks, in increasing order of strength:

```sql
-- (a) The grant. Expect SELECT, INSERT, UPDATE, DELETE and no DDL of any kind.
SHOW GRANTS FOR '<app-db-user>'@'%';

-- (b) The triggers. Expect exactly two rows. Must be run as ROOT — the app credential
--     deliberately lacks TRIGGER, so it sees zero rows on a correctly hardened instance.
SELECT TRIGGER_NAME, EVENT_MANIPULATION
  FROM information_schema.TRIGGERS
 WHERE EVENT_OBJECT_TABLE = 'audit_log' AND EVENT_OBJECT_SCHEMA = '<database>';
```

(c) The credential-independent one, and the best of the three: **`php artisan backup:run`
succeeded in §1.3.** Its pre-flight inserts a throwaway `audit_log` row, attempts an UPDATE and a
DELETE, and aborts the whole backup with *"A live probe against audit_log was NOT blocked by: …"*
if either succeeds. A green backup is positive proof the triggers are live.

If (a) shows DDL privileges or (b) shows fewer than two triggers, re-run
`docs/sql/least-privilege.sql` using the exact `${var//…/…}` substitution recipe at its lines
49–55 — **bash parameter expansion, not `sed`**, which eats the backslash, and
`{{DATABASE_ESCAPED}}` substituted before `{{DATABASE}}`.

There is no standalone "was it ever applied?" one-liner in the repo; the verify block lives at
the tail of the same file and still needs its placeholders substituted. The three checks above
are that one-liner, written out.

### 6.3 Check the database's session timezone

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot \
  -e "SELECT @@global.time_zone, @@session.time_zone, NOW(), UTC_TIMESTAMP();"
```

After this deploy expect `+00:00` for both (§3.4's new `--default-time-zone` flag). Before it,
expect `SYSTEM`. `NOW()` and `UTC_TIMESTAMP()` should agree.

This is not cosmetic. `audit_log.created_at` is a MySQL `TIMESTAMP` — stored as UTC, re-rendered
per the **session** zone on every read — and `AuditChain::canonical()` v3 hashes that rendered
string verbatim, deliberately, so that an `APP_TIMEZONE` change can never re-render history. It
was reproduced empirically: an intact 20-row chain, `SET GLOBAL time_zone='+03:00'` against the
same unchanged rows, verification broken at row 1; reverting made it intact again. **Never run
`SET GLOBAL time_zone` against this database.**

### 6.6 Two standing hazards this deploy introduces

**Both were measured in the rehearsal, in both directions, and both behave exactly as stated:**

- **`db:seed --force` re-asserts `units.name` on every run.** `ReferenceSeeder` writes `name`

### 6.7 The first backup after the slug change

Setting `INSTANCE_SLUG=qch` changes the archive filename from
`endorsement-<Str::slug(APP_NAME)>-…` to `endorsement-qch-…`. The retention sweep's glob is
**anchored per slug** (so `qch` cannot match `qch-2`), which means the old-named archives are no
longer in `--keep`'s window — `BackupRun` counts foreign-slug archives and **warns**, but never
prunes them. Expect that warning on the first run after the change; it is not a fault. Delete the
old-named archives by hand once you are satisfied the new ones restore.

## 7. Rollback, honestly

**There is no clean rollback for this deploy past migration #6.** Everything below is written to
make that concrete rather than to offer a `down()` that half-works.

### 7.1 Before migration #6 has run

Coolify → Deployments → the last good one → Redeploy. Complete and lossless. This is the only
window in which "roll back the code" means anything.

### 7.2 After migration #6 has run

`users.full_name` and `users.position` no longer exist, and the `8886f8d` image names both — from
`HandleInertiaRequests`, which runs on every page. **Redeploying the old image does not produce a
site that 500s. It produces a site that answers `/up` with 200 and every `cap:` route with 403**,
with all three monitors green and no alert anywhere. §0 has the measurement and the reasoning; the
practical point here is that "the rollback looked fine" is exactly what it will look like.

Your options are:

1. **Roll forward.** Fix the defect, push, deploy. For anything short of data corruption this is
   the right answer.
2. **Restore the §1.3 backup and redeploy `8886f8d`.** This discards every clinical write made
   since the backup was taken. It is a decision about patient records, not about software.

`migrate:rollback` is a third option only in the narrow case where the *schema* is the problem and
no new data has been entered. Read §7.3 before considering it.

### 7.3 What `migrate:rollback` actually does here

> **This section described an operation nobody had ever run, and until 2026-08-12 it would not have
> worked.** The rehearsal executed `migrate:rollback` for the first time in this repository's life
> and it failed at **three** separate `down()` methods, each with
> `error in index <name> after drop column: no such column: "<column>"`:
> `2026_08_14_120002` (`promotion_batch_id`), `2026_08_10_120005` (`person_id`) and
> `2026_08_10_120001` (`person_id`). `dropConstrainedForeignId()` emits `dropForeign` +
> `dropColumn` and **nothing that removes a separate index on the same column**, and SQLite will
> not drop a column an index still names.
>
> The third is the instructive one: its `down()` carried a comment asserting the opposite as fact,
> a belief the 2026-08-09 MySQL rehearsal left behind when it fixed InnoDB's *"1553 Cannot drop
> index … needed in a foreign key constraint"* by deleting the `dropUnique()` call. **The two
> engines constrain opposite ends of the same statement.** The order that satisfies both is
> **constraint, then index, then column**.
>
> **All three are fixed** (`3967ca4`), with `tests/Feature/Build/MigrationChainRollsBackTest.php`
> reversing the whole chain and re-applying it — the first test here that ever calls a `down()`.
> After the fix all 22 reverse in 1.0 s and the result is the `8886f8d` schema, with 13 users, 146
> handovers, 45 sign-offs, 4 invitations and 63 audit rows intact and `audit:verify` green. **This
> paragraph is only about SQLite; the whole section below is still untested on MySQL** (§9.0).

All 22 run in **one batch**, so a bare `php artisan migrate:rollback` reverses **all 22** in
reverse file order. That order happens to be correct — #6 (`move_name_and_position_off_users`)
unwinds *before* #4 (`create_people_and_link_users`), which is the mandated sequence — and the
identity subset was verified clean against real MySQL 8.4 in the 2026-08-09 rehearsal. Use
`--step=N` to reverse exactly N migrations instead (`Migrator::getMigrationsForRollback()`:
`--step` counts migrations, not batches).

> **A ROLLBACK THAT STOPS HAS ALREADY DESTROYED EVERYTHING BELOW WHERE IT STOPPED**
>
> `migrate:rollback` is **not** atomic across the batch. It reverses migrations one at a time,
> newest first, and each one that succeeds is done — committed, its tables dropped, its row removed
> from `migrations`. When the rehearsal's run refused at #16, the five migrations after it had
> **already been reversed**:
>
> ```
> 2026_08_16_120002_create_demo_rows_table ................ DONE
> 2026_08_16_120001_create_clinics_and_attendees_tables ... DONE
> 2026_08_15_120004_create_vacations_table ................ DONE
> 2026_08_15_120003_create_master_rota_assignments_table .. DONE
> 2026_08_15_120002_correct_ward_clinic_owner ............. DONE
> 2026_08_14_120002_add_provenance_to_person_levels ....... FAIL
> ```
>
> `migrations` held 39 of 44 rows, and the rota, the vacations, the clinics and the demo ledger
> were gone. **The same is true of migration #17's refusal, which is not a defect at all.** Its
> `down()` throws rather than truncate a clinical field over `TEXT`'s 65,535 bytes — measured, with
> a 95,976-byte row — and by the time it speaks, five tables below it no longer exist.
>
> **So: a stopped rollback is not a paused rollback.** Do not respond to one by fixing the
> obstruction and running `migrate:rollback` again — that reverses *more*. The recovery from a
> rollback that stopped part-way is **restore the §1.3 backup**, exactly as it is for a rollback
> that ran to completion. Read the per-migration table below as *"what you lose by the time the
> rollback reaches this row"*, not as a list of independent choices.

It needs `DROP` in addition to the deploy grant, granted for the one operation and revoked
immediately:

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "GRANT ALTER, CREATE, REFERENCES, DROP ON \`$DBNAME\`.* TO '$DBUSER'@'%'; FLUSH PRIVILEGES;" && {
  sudo docker exec -u app "$APP" php artisan migrate:rollback --step=1 --force; rc=$?
  sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "REVOKE ALTER, CREATE, REFERENCES, DROP ON \`$DBNAME\`.* FROM '$DBUSER'@'%'; FLUSH PRIVILEGES;"
  echo "rollback exit=$rc"
}
```

Per migration, honestly:

| # | Migration | `down()` | What reversing costs |
|---|---|---|---|
| 22 | `create_demo_rows_table` | `dropIfExists` | **Loses the demo ledger.** If a demo department exists, it becomes permanently unremovable — the ledger is the only record of which rows were never real. Remove the demo department *first*. |
| 21 | `create_clinics_and_attendees_tables` | `dropIfExists` ×2 | Every clinic definition and attendee rule, gone. |

For anything that has real data in it, restore-from-backup is the answer, and this document says

## 9. MySQL-only hazards

The suite is 1,680 tests on SQLite `:memory:`. Production is MySQL 8.4 with
`utf8mb4_unicode_ci` (`config/database.php` line 67) — **not** MySQL 8.4's own default
`utf8mb4_0900_ai_ci`. This section is what that difference hides. Everything below was read; the
three marked **verified here** were reproduced.

### 9.0 Two rehearsals, and what neither of them establishes

**There are two, on two engines, and they answer different questions. Do not let one stand in for
the other.**

**(A) The 2026-08-09 MySQL rehearsal** (`docs/superpowers/plans/2026-08-15-mysql-production-defects.md`)
ran the chain *as it stood that day* against real MySQL 8.4 on throwaway stacks. It found four
defects, **all fixed and in this tree**: the migration grant (`ALTER, CREATE, REFERENCES`, `+DROP`
for rollback, `INDEX` never needed); the `TEXT` byte ceiling and the 1.783× encrypted-envelope
growth constant; `2026_08_10_120001`'s `down()` ordering (`dropUnique` before
`dropConstrainedForeignId` → `1553`); and WARD's `clinic_owner`.
`docs/superpowers/plans/2026-08-08-p0b-bounded-custom-fields.md` records the fifth: an encrypted
payload must never live in a `json()` column. It did **not** include `2026_08_16_120001` or
`2026_08_16_120002`, which landed 2026-08-11 — both plain `Schema::create` with `constrained()`
FKs, the shape it had already characterised. **And one of its own fixes was wrong in the other
direction** — deleting a `dropUnique()` call to satisfy InnoDB left a `down()` that SQLite refuses
(§7.3). A single-engine fix to a two-engine problem is its own hazard.

**(B) The 2026-08-12 upgrade-path rehearsal** (`docs/REHEARSAL-UPGRADE-2026-08-12.md`) ran the
real forward path — `migrate --force` from `8886f8d` against a populated database — for the first
time ever. **On SQLite**, because Docker was down and MySQL was unavailable. It established §0's
reassurances and found the three `down()` defects of §7.3.

**What (B) structurally could NOT show, and what therefore remains unverified on the engine
production actually uses:**

1. **`ALGORITHM=COPY` on migration #17.** SQLite rewrites the table cheaply and reported 72 ms.
   MySQL 8.4 cannot apply `TEXT` → `MEDIUMTEXT` in place and rebuilds `handovers` **four times**,
   once per column, blocking writes throughout. §1.6's sizing is entirely unverified and the
   rehearsal's timing is actively misleading about it. Same for that migration's `down()`.
2. **Non-transactional DDL — the big one.** See the box below.
3. **Collation.** `utf8mb4_unicode_ci` is case- and accent-insensitive and PAD SPACE.
   `users.member_name`, `people.short_name`, `levels.code` and `unit_field_definitions.key` all
   compare differently there. The rehearsal deliberately created a case-colliding `member_name`
   pair (`ahmed.k` / `Ahmed.K`) that MySQL's UNIQUE index would have refused outright — §9.3's
   query reported it correctly, but it could only exist because the engine was SQLite.
4. **`lockForUpdate()`.** `SQLiteGrammar::compileLock()` returns `''`, so all four call sites —
   the audit chain tail above all — were no-ops in the rehearsal exactly as they are in the suite
   (§9.7). A forked chain under concurrency is not reachable on this engine.
5. **`DATE` truncation.** §9.1's MySQL half is still *reasoned, not measured*.
6. **Privileges.** `GRANT ALTER, CREATE, REFERENCES` was verified by reading all 22 `up()`
   methods, not by running under a restricted credential. SQLite has no privilege model.
7. **JSON columns.** MySQL re-serialises a `JSON` column on `SELECT` (§5.1's space-after-comma)
   and rejects the base64 an encrypted payload puts in one. SQLite maps `json()` to TEXT; no
   difference is observable.
8. **Index usage.** Every `EXPLAIN` question in §9.6 is unanswerable there.
9. **The real data volume.** 146 handovers, not tens of thousands. Read every rehearsal timing as
   *"the migration ran"*, never as *"the migration is fast"*.
10. **The deploy mechanics themselves.** Coolify, the container recreate caused by the new
    `db.command`, the `INSTANCE_SLUG` rename and its effect on backup retention, `ext-intl` and
    the Umm al-Qura data in the built image, `scripts/verify-live.sh`, and the backup/restore
    drill are all outside a local worktree entirely. **None of §1, §3, §4.1, §6 or §8 has been
    rehearsed by anything.**

> **NON-TRANSACTIONAL DDL: 18 OF THE 22 MIGRATIONS EMIT MORE THAN ONE STATEMENT**
>
> SQLite has transactional DDL, so every migration in rehearsal (B) was all-or-nothing and **no
> migration could half-apply**. **MySQL has none.** A `Schema::create` whose `CREATE TABLE` commits
> and whose `ADD CONSTRAINT` then fails leaves a table that exists and is *not* recorded in
> `migrations` — the `1050 Table already exists` trap §4.2 documents, which a re-run turns into
> what looks like a new problem. **Nothing in rehearsal (B) could have produced that failure.**
>
> The exposure is far wider than either the rehearsal or an earlier draft of this file said.
> Compiled against Laravel's own MySQL grammar in this tree (`laravel/framework` v13.21.1;
> `Blueprint::toSql()` emits one entry per command, `MySqlGrammar::compileAdd()` **one `alter table

### 9.1 A `date` column compares wrongly on the boundary day — the comments named the wrong engine

**Corrected 2026-08-12** (branch `docs/date-cast-comment-correction`). This section previously
presented a two-engine comparison under one **"Verified here"** heading when only the SQLite half
had been run. The measured and the reasoned halves are now separated, because that conflation is
the same class of error as the inverted attribution it was reporting.

**MEASURED**, in-process on this tree, SQLite 3.53, a model with `protected $casts = ['d' =>
'date']` over five consecutive rows:

```
RAW STORED:  "2026-08-12 00:00:00"   typeof = text   (SQLite has no DATE type; NUMERIC
                                                      affinity, non-numeric value → verbatim)

Needle '2026-08-12', bare operator vs. the whereDate() it should equal:

  op    bare where()          whereDate()               verdict
  =     (none)                08-12                     WRONG — boundary day lost
  <=    08-10,08-11           08-10,08-11,08-12         WRONG — inclusive bound silently isn't
  >     08-12,08-13,08-14     08-13,08-14               WRONG — exclusive bound silently isn't
  <     08-10,08-11           08-10,08-11               agrees
  >=    08-12,08-13,08-14     08-12,08-13,08-14         agrees
```

Also verified at source, no server needed: `getDateFormat()` is defined on
`Illuminate\Database\Grammar` as `Y-m-d H:i:s` and overridden **only** by `SqlServerGrammar` —
so both engines are *sent* `'2026-08-12 00:00:00'`.

The stored value sorts strictly **after** the bare `Y-m-d` needle for the same day, so the entire
error is confined to the **boundary day**. Three of five operators are wrong and two are right by
luck — which is why the rule is stated over the column, not the operator.

**REASONED, NOT MEASURED:** a MySQL `DATE` column is expected to truncate the time component on
storage, which would make the bare comparison *succeed* there. This follows from the column type,
but it has not been run: Docker's daemon was down when this was written, and **nothing in this
repository has ever executed against MySQL.** Treat it as an inference. If a MySQL instance ever
becomes available, run the matrix above against it and replace this paragraph with the result.

What *is* established regardless of the engine question: **use `whereDate()`, never a bare
comparison against a cast date column.** That is correct on both engines, which is why nothing is
broken today.

**Six code comments stated this backwards and are now fixed** — they blamed "the engine
production runs", i.e. MySQL, for behaviour measured on SQLite.
`app/Http/Controllers/EndorsementController.php`'s `updateSignoff()` now carries the canonical
statement and the measurement; `Period::booted()`, `MasterRotaAssignment::booted()`,
`Vacation::booted()`, `ClinicRoster::rotatingOn()`, `RotaController::landingYear()` and
`DepartmentSetup::steps()` cite it. Recorded as **ruling 72** in `docs/spec/15-rulings.md`.

**No code was wrong** — every call site already used `whereDate()`. A permissive sweep for a bare
comparison against any of the eight `date`-cast columns across `app/` and `database/` returned
nothing. Only the stated reason was wrong.

### 9.2 `levels.code` is UNIQUE with no case normalisation — one CSV, two outcomes

`levels.code` is `string(20)->unique()` and `Level` carries **no** `code` mutator — deliberately,
and `app/Http/Requests/Admin/LevelRequest.php`'s docblock says so explicitly (*"Unlike
`Unit::code`, `Level::code` carries no write-time mutator"*). `Unit::code` **does** normalise
(`strtoupper(trim(...))`, and `Unit::findByCode()` uppercases the needle), which is exactly the
asymmetry.

`app/Support/Roster/RosterImport.php` line 307 looks a level up with
`Level::query()->where('code', $levelRaw)->first()` on raw CSV text — while line 295 immediately
above it *does* fold case for `Position` via `whereRaw('LOWER(name) = ?')`.

**What this means for the first roster import:** a file containing `r1` **imports cleanly on
production** and is refused with *"unknown level code"* in any SQLite rehearsal. And
`ReferenceSeeder`'s `Level::firstOrNew(['code' => $code])` will *match* an administrator-renamed
differently-cased row on MySQL (no-op) but *miss* it on SQLite (duplicate insert).

```sql
-- Must return no rows. Run after §4.3.
SELECT LOWER(code) AS folded, COUNT(*) FROM levels GROUP BY folded HAVING COUNT(*) > 1;
```

### 9.3 `users.member_name` is case-insensitive on production and case-sensitive in every test

`app/Http/Controllers/Auth/AuthenticatedSessionController.php` line 70 is
`User::where('member_name', $data['member_name'])->first()` with no normalisation on read or
write — while the brute-force throttle key three lines above *is* `Str::lower(...)`ed.

Two consequences:

- **Auth:** on production `AHMED` signs in as `ahmed`. Every login test proves the opposite.
- **Provisioning — this is the one that will surprise you.** `Rule::unique('users','member_name')`
  (`InvitationAcceptController`, `UserManagementController`) will **reject** a new handle that
  differs only in case from an existing one, **including a soft-deleted account's**, which still
  holds the index. An invitation-acceptance flow green in the suite can 422 on production.

```sql
-- Expect 0 (MySQL would already have refused a collision). Worth running anyway, because it
-- is also the check on any historical LegacyImport output.
SELECT LOWER(member_name) AS folded, COUNT(*) FROM users GROUP BY folded HAVING COUNT(*) > 1;
SELECT LOWER(short_name)  AS folded, COUNT(*) FROM people WHERE short_name IS NOT NULL
 GROUP BY folded HAVING COUNT(*) > 1;
```

The first query was exercised against a deliberately planted `ahmed.k` / `Ahmed.K` pair and
reported it (`ahmed.k  2`). **That pair could only exist because the rehearsal ran on SQLite** —
MySQL's UNIQUE index would have refused the second row on insert. On production this is a check on
historical `LegacyImport` output, and a non-empty result there means something bypassed the index,
not that the index is missing.

### 9.4 `people.short_name`, and the two importers that resolve through it

Same collation mechanism, three live call sites:

- **`app/Support/Rota/RotaImport.php` line 983** — `Person::withTrashed()->where('short_name',
  $handle)`. Worse than a plain lookup difference, because the cell key at line 446 folds case
  *only when the person is null*. For a file containing both `ahmed` and `AHMED`: on **MySQL**
  both resolve to one person and become **one** cell whose spans are overlap-checked; on
  **SQLite** one resolves and one does not, producing a second, unresolved cell. Identical bytes,
  two import outcomes.
- **`app/Support/Roster/RosterImport.php` lines 353 and 440/451** — the secondary match key and
  the `crossMatchErrors()` collision pre-flight. Here MySQL is the *stricter* engine: a roster
  file that imports clean against SQLite produces per-line *"short name belongs to a different
  person already on the roster"* refusals on production.

**Practical instruction: do the roster dry-run preview against production, not against a local
rehearsal.** The preview is the deliverable, and it is the only place these two engines agree to
tell you the truth.

### 9.5 Row order on the rota grid and export is not reproducible on MySQL

`App\Support\Rota\RotaGrid` orders people in SQL (`orderBy('people.full_name')`, line 102) and,
in the stale-rows branch only, re-sorts in PHP (`sortBy(...)`, line 128); `usort()` at lines
222–227 relies on PHP's stable sort to preserve ties. On SQLite both orderings are byte order, so
they agree. On MySQL `utf8mb4_unicode_ci` is case- **and accent**-insensitive: `Ahmed Ali` and
`ahmed ali` collate **equal**, as do Arabic alef variants, and MySQL's order among equal keys is
unspecified. So the grid can render in a different order depending on whether stale rows exist,
and the "stable" tie order is not reproducible between page loads.

Same shape in `RotaExport` (SQL `orderBy('starts_on')` then PHP `sortBy(readingOrder)`), whose
stated purpose — *"a diff between two exports of the same year is legible"* — does not hold on
MySQL for two people sharing a `full_name`.

**Watch for:** an export diff that shows spurious moves. Not a correctness bug; do not chase it as
one.

### 9.6 Every range read on the new rota tables uses `whereDate()`, which is non-sargable on MySQL

The new migrations create exactly the indexes these reads want —
`master_rota_assignments(starts_on, ends_on)`, `vacations(starts_on, ends_on)`,
`periods(starts_on, ends_on)`, `handovers(unit_id, handover_date)` — and **47** `whereDate()` /
`orWhereDate()` call sites across sixteen files wrap the column in a function, because of §9.1's
rule. MySQL compiles `whereDate()` to
`date(col) op ?`, and a wrapped column generally cannot use the index.

With 1,680 in-memory tests over a handful of rows this is structurally invisible. **Verify with
`EXPLAIN` once real data exists** — the rota grid for a full academic year, and the handover day
index:

```sql
EXPLAIN SELECT * FROM master_rota_assignments
 WHERE DATE(starts_on) <= '2027-06-30' AND DATE(ends_on) >= '2026-07-01';
EXPLAIN SELECT handover_date, COUNT(*) FROM handovers
 WHERE unit_id = 1 AND DATE(handover_date) >= '2026-07-01' GROUP BY handover_date;
```

`type: ALL` means a full scan. The fix is a half-open range (`>= $from AND < $toPlusOne`), which
is index-friendly **and correct on both engines** given §9.1's storage facts. Do not attempt it
during this deploy.

### 9.7 Locks that are no-ops in every test

`SQLiteGrammar::compileLock()` returns `''`, so `lockForUpdate()` is compiled away in all 1,680

| `app/Http/Controllers/Auth/InvitationAcceptController.php:88` | Two people opening one invitation link at once |
| `…:121` | The person row while the account is claimed |

### 9.8 Lower-priority, recorded so they are not rediscovered

- **The collation is PAD SPACE and that is not MySQL 8.4's default.** `utf8mb4_unicode_ci` treats
  `'PICU'` and `'PICU '` as equal for comparison *and* for UNIQUE; `utf8mb4_0900_ai_ci` (the
  server default) does not. Mitigated in practice — Laravel's global `TrimStrings` is not removed
  and both CSV readers trim every value — so the two never meet. Recorded because the choice is
  deliberate and divergent, and because it is the same property that makes §9.5 accent-insensitive.
- **`App\Support\UnitMerge`'s field-key pre-flight** compares keys with an exact PHP string match
  while the constraint it guards, `unique(unit_id, key)`, folds case on MySQL. Its comment claims
  a database guarantee that is not there. Unreachable today — `UnitFieldDefinition::booted()`
  enforces `^[a-z][a-z0-9_]{0,63}$` on save — so only a raw SQL insert could produce a
  `Weight`/`weight` pair.
- **`LegacyImport` has never run against MySQL either.** It matches and upserts on
  `member_name`; two legacy rows differing only in case **collapse into one `users` row** on
  MySQL and stay two on SQLite. Its own reconciliation counts will surface it — treat a mismatch
  there as this, not as a new bug. Only relevant if the owner ever changes their mind about the
  import (`docs/RUNBOOK-IMPORT.md`).
- **`handovers.extra_fields` is still `TEXT`** and was deliberately not widened by #17. It is
  bounded at 32,000 pre-encryption bytes by `EncryptedJson::MAX_BYTES`, which at the measured
  1.783× envelope growth is ~57,056 bytes against `TEXT`'s 65,535 — safe, but a **13% margin**.
  If that growth constant is ever re-measured higher, this is the next column to overflow.
- **Non-atomic DDL is not confined to the one migration the standing runbook names, and it is
  wider than "a few multi-statement ones".** Moved to §9.0's box and re-derived there: **18 of the
  22** emit more than one statement, only three are a single DDL statement, and one added column is
  one `ALTER` — Laravel's `MySqlGrammar::compileAdd()` does not merge them. An earlier draft of
  this bullet named eight migrations; that undercounted by ten.
