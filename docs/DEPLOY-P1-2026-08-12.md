### The single most important fact in this document

> **Once migration `2026_08_10_120003_move_name_and_position_off_users` has run, redeploying the
> previous image is no longer a rollback — it is an outage.**

That migration DROPs `users.full_name` and `users.position`. The `8886f8d` code reads both as
real columns in twelve files, including `app/Http/Middleware/HandleInertiaRequests.php`, which
runs on *every* page. Old code against the new schema fails on the first request, not on some
obscure screen.

So this deploy has two regimes, and you cross the line in the middle of §4:

- **Before that migration** — Coolify → Deployments → previous → Redeploy is a complete,
  lossless rollback.
- **After it** — the only recoveries are *roll forward* (fix and redeploy) or *restore the
  pre-deploy backup and redeploy `8886f8d`*, which discards every clinical write made since
  the backup. §7 is the honest version of this.

Plan the window accordingly: this is not a deploy to start at 16:00 on a Thursday.

### The three that are not routine

**#6 `move_name_and_position_off_users` — the one-way door.** Covered in §0. Take the extra dump
the standing runbook asks for before you start §4:

```bash
PW=$(sudo docker exec "$DB" printenv MYSQL_ROOT_PASSWORD)
sudo docker exec -e MYSQL_PWD="$PW" "$DB" \
  mysqldump -uroot --single-transaction --routines "$DBNAME" > pre-p1-$(date +%F).sql
```

**#17 `widen_rich_text_handover_columns` — the slow one, and it is four passes, not one.**
MySQL 8.4 refuses both `ALGORITHM=INSTANT` and `ALGORITHM=INPLACE` for `TEXT`→`MEDIUMTEXT` (the
on-disk length prefix widens, 2 bytes → 3) and falls back to `ALGORITHM=COPY`, rebuilding
`handovers` row by row. Reads continue; **writes to `handovers` block** — an endorsement save
queues rather than fails, so this presents as "the app got slow", not as an error.

Compiled against Laravel's own MySQL grammar (`Illuminate\Database\Schema\Grammars\MySqlGrammar::
compileChange()` emits one statement per column), the migration issues **four** separate
statements:

```sql
alter table `handovers` modify `disease` mediumtext null;
alter table `handovers` modify `details` mediumtext null;
alter table `handovers` modify `plan`    mediumtext null;
alter table `handovers` modify `nevent`  mediumtext null;
```

Each is its own COPY rebuild. `docs/superpowers/plans/2026-08-09-ops-rehearsal-defects.md` line
285 records *"~26 MB/s: 20,000 rows / 157 MB ≈ 6 seconds"* but does **not** say whether that
timed one statement or all four. Size it both ways from §1.6 and plan for the worse:

- optimistic (the figure was end-to-end): `table_MB / 26` seconds
- conservative (the figure was one pass): `4 × table_MB / 26` seconds

COPY is atomic per statement — either a rebuild lands or the original table is untouched — so
this is a *waiting* risk, not a data-loss risk.

**#1 `add_configuration_to_units` — `active` defaults FALSE and the backfill is code-matched.**
A `units` row whose `code` is not one of the four constants is left `active = 0` and `bar_class
IS NULL`, and stops being routable. That is deliberate (fail closed). §5.1's counter-check is what
surfaces it — `display_order` alone gives no signal, since a missed row just sorts to the end.

### Privileges

The forward run needs **`ALTER, CREATE, REFERENCES`** and nothing more. Confirmed by reading all
22 `up()` methods: none calls `dropIfExists` or `DROP TABLE`, so **`DROP` is not needed to
migrate** (it *is* needed to roll back — §7). `INDEX` is not needed; `2026_08_10_120003`'s index
drop is emitted as `alter table users drop index ...`, which `ALTER` covers.

Two caveats on the standing runbook's *"verified across the full chain"* claim: that verification
was the 2026-08-09 MySQL rehearsal, which predates migrations **#21 and #22** (added 2026-08-11).
Both are plain `Schema::create` with `constrained()` foreign keys — the identical shape the
rehearsal already proved needs `CREATE` + `REFERENCES` — so the grant is unchanged, but they
were not in the measured run.

`php artisan db:seed --force` needs **no** elevated privilege. Verified: the seeders contain no
`Schema::`, no `TRUNCATE`, no `DB::statement`, no raw SQL — only SELECT/INSERT/UPDATE and one
no-op `DELETE`. Revoke before you seed.

### 3.1 Compose passthrough — verified present, with explicit `${VAR:-default}`

P0d Task 9 found that a variable taught to `config/` and set in Coolify but never referenced in
this file's `environment:` block has **zero** effect on the running container. Every variable
this release depends on is now wired, and each is pinned by a test:

| Variable | Compose line | Guard |
|---|---|---|
| `APP_TIMEZONE` | `${APP_TIMEZONE:-Asia/Riyadh}` | `DeploymentInvariantsTest::test_the_deployment_timezone_is_settable_and_defaults_to_the_ward` |
| `INSTANCE_SLUG` | `${INSTANCE_SLUG:-}` | `…::test_instance_and_institution_variables_reach_the_container` |
| `INSTITUTION_CODE` | `${INSTITUTION_CODE:-QCH}` | same |
| `INSTITUTION_NAME` | `${INSTITUTION_NAME:-Qatif Central Hospital}` | same |
| `HIJRI_OFFSET_DAYS` | `${HIJRI_OFFSET_DAYS:-0}` | `…::test_hijri_offset_reaches_the_container` |

The `:-default` half matters as much as the passthrough: Laravel resolves a **present-but-empty**
key to `''`, not to `env()`'s default, and an unset Coolify variable interpolates to empty here —
not to absent.

### 3.2 `INSTANCE_SLUG=qch`

Set it in Coolify → `endorsement` → Environment Variables **before you deploy**. It names the
backup archive, scopes that archive's own retention sweep, and names the host scripts'
config/log/state files. `App\Support\Instance::slug()` reads it through `config()` (so the
entrypoint's `config:cache` is authoritative), requires `/^[a-z0-9][a-z0-9-]{0,31}$/`, **throws**
rather than normalising a bad value, and falls back to `Str::slug(APP_NAME)` when empty.

Confirm after the deploy:

```bash
sudo docker exec "$APP" printenv INSTANCE_SLUG        # expect: qch
sudo docker exec -u app "$APP" php artisan instance:show
```

`instance:show` reports slug, institution, timezone, `APP_KEY` fingerprint and each owner-managed
secret as `set` / `NOT SET` — **no secret value is ever printed**
(`app/Console/Commands/InstanceShow.php`).

**Do this before the next 01:30 backup.** The archive name is derived when `backup:run` executes,
not retroactively. See §6.7 for what the rename does to retention.

### 3.3 `HIJRI_OFFSET_DAYS=-1`

QCH's calibration, established against the department's own published calendar across a month
boundary. Without it every Hijri date renders **one day late, with no error anywhere**.

> **Correction to `docs/RUNBOOK-DEPLOY.md`.** That document (in its P1a verification section)
> says re-running `db:seed --force` *"will NOT overwrite an existing non-null value"*, so a wrong
> value *"must be corrected by hand"*. **That is not what this tree does.**
> `ReferenceSeeder` (lines 176–191) writes `institutions.hijri_offset_days` from the environment
> whenever the config value is neither `null` nor `''` — and because `docker-compose.production.yml`
> passes `${HIJRI_OFFSET_DAYS:-0}`, the variable is **always present** in the container, defaulting
> to the string `"0"`. So the seeder writes this column **on every deploy**.
>
> Two consequences:
> 1. **Good, for today:** set `HIJRI_OFFSET_DAYS=-1` in Coolify before the deploy and
>    `db:seed --force` applies it. No hand `UPDATE` is needed.
> 2. **A standing hazard from today onward:** `hijri_offset_days` is *also* editable at
>    Admin → Structure → Calendar (bounded `[-2, 2]`, audited). An administrator who recalibrates
>    there and does not also change the Coolify variable will have it **silently reverted on the
>    next deploy**. Treat the Coolify value as the source of truth and change both together.
>
> The seeder's own docblock claims it is "NEVER reverted to 0 by a re-seed"; that claim holds only
> when the variable is *absent*, which this compose file guarantees it is not.

An out-of-range value is refused loudly — `ReferenceSeeder` throws
`InvalidArgumentException` outside `[-2, 2]`, which will fail the seed step, not corrupt the row.

Verify after §5:

```bash
sudo docker exec -u app "$APP" php artisan tinker \
  --execute="echo App\Models\Institution::current()->hijri_offset_days;"      # expect -1
```

Then do the real check, which is not a number: open **Admin → Structure → Calendar**, which shows
today's Gregorian and Hijri labels side by side computed exactly as every clinical screen computes
them, and compare two consecutive days across a Hijri month boundary against the department's own
published calendar.

### 3.4 What else changed in the compose file

- **`APP_TIMEZONE` became a variable** (was the literal `Asia/Riyadh`). Leave it unset in Coolify;
  the default is unchanged. `APP_TIMEZONE` must be correct before the first clinical write —
  `now()` moves with it and the handover day boundary moves under existing rows. It already is.
- **`--default-time-zone=+00:00` is new on the `db` service.** This pins MySQL's session zone,
  which `audit_log.created_at` (a `TIMESTAMP`) is re-rendered through on every read, and which
  `AuditChain::canonical()` v3 hashes verbatim. Before this flag it tracked `SYSTEM` and could
  drift across a base-image bump — making `audit:verify` declare the whole trail broken with
  nothing having changed. It pins today's already-correct value (UTC); no stored row changes.
  **Operational consequence: changing `db.command` means Docker recreates the database
  container on this deploy.** The `endorsement-db` volume persists, but expect a short database
  outage during the deploy and confirm the db healthcheck goes green before §4.

## 4. The deploy

```bash
git push origin main
```

Then **Deploy** in Coolify. The container does not migrate at boot —
`docker/entrypoint.sh` never touches the schema, so an unattended restart can never alter a
clinical database. It rebuilds config/route/view caches as `app` (not root) and refuses to start
without `APP_KEY`. It *will* print a pending-migration banner; that is the entrypoint doing its
job, not a failure.

### 4.1 Before the migrations, prove the image

`ext-intl` was a deploy blocker once — the production image did not build at all
(commit `6e21336`). It is now installed in both the vendor stage (so composer's platform check is
genuinely satisfied) and the runtime stage (`Dockerfile` lines 114–117: `docker-php-ext-install
… pdo_mysql gd intl zip bcmath gmp opcache`). CI builds the image on every push. Confirm it
inside the container you actually deployed:

```bash
sudo docker exec "$APP" php -m | grep -i intl        # expect: intl
sudo docker exec "$APP" php -r 'echo PHP_VERSION, "\n";'   # expect 8.4.x
```

And prove intl *works*, not just that it loads — the whole calendar module depends on it:

### 4.2 Migrate — grant, migrate, revoke

Unchanged from `docs/RUNBOOK-DEPLOY.md`, reproduced so this file is runnable on its own:

```bash
eval "$(sudo bash docker/instance-env.sh oo7d7si62yhyi7fx10hrck6q)" && \
PW=$(sudo docker exec "$DB" printenv MYSQL_ROOT_PASSWORD) && \
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "GRANT ALTER, CREATE, REFERENCES ON \`$DBNAME\`.* TO '$DBUSER'@'%'; FLUSH PRIVILEGES;" && {
  sudo docker exec -u app "$APP" php artisan migrate --force; rc=$?
  sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "REVOKE ALTER, CREATE, REFERENCES ON \`$DBNAME\`.* FROM '$DBUSER'@'%'; FLUSH PRIVILEGES;"
  echo "migrate exit=$rc"
}
```

Up to and including the `GRANT`, `&&` is load-bearing — `instance-env.sh` prints `false` on
refusal, so a refusal aborts everything. Past the `GRANT`, the brace group runs the `REVOKE`
**unconditionally**: a failed migration is exactly when elevated privileges must not linger while
you debug.

Then verify the revoke actually landed:

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "SHOW GRANTS FOR '$DBUSER'@'%';"
```

Expect `SELECT, INSERT, UPDATE, DELETE` and **none** of `ALTER`, `CREATE`, `REFERENCES`, `DROP`.

**If `migrate exit=` is non-zero, do not just re-run it.** MySQL has no transactional DDL: a
`Schema::create` with a foreign key commits the `CREATE TABLE` and can then fail on the separate
`ADD CONSTRAINT`, leaving a partially built table that is *not* recorded in `migrations`. Retrying
then produces `1050 Table already exists`, which reads like a new problem and is not. Follow
`docs/RUNBOOK-DEPLOY.md`'s five-step recovery ("If `migrate exit=` is non-zero"): `migrate:status`
names the failed migration as the first still-Pending row; read its `up()`; check for each object
it creates; drop residue as root; then retry.

### 6.2 Confirm `least-privilege.sql` was ever applied

Its underscore-escaping bug (fixed in `416227d`, 2026-08-09) meant it could silently apply
**nothing**: MySQL stores `_` and `%` as wildcards in `mysql.db.Db`, and the official image's
auto-grant stores the database name escaped (`endorse\_live`). The old script's
`REVOKE ... ON \`endorse_live\`.*` matched no stored grant, failed with `ERROR 1141`, and aborted
the batch **before creating the triggers** — leaving the credential on `ALL PRIVILEGES` and no
append-only protection, while looking like it had run.

Three checks, in increasing order of strength:

```sql
-- (a) The grant. Expect SELECT, INSERT, UPDATE, DELETE and no DDL of any kind.
SHOW GRANTS FOR '<app-db-user>'@'%';

-- (b) The triggers. Expect exactly two rows. Must be run as ROOT — the app credential
--     deliberately lacks TRIGGER, so it sees zero rows on a correctly hardened instance.
SELECT TRIGGER_NAME, EVENT_MANIPULATION
  FROM information_schema.TRIGGERS
 WHERE EVENT_OBJECT_TABLE = 'audit_log' AND EVENT_OBJECT_SCHEMA = '<database>';
```

(c) The credential-independent one, and the best of the three: **`php artisan backup:run`
succeeded in §1.3.** Its pre-flight inserts a throwaway `audit_log` row, attempts an UPDATE and a
DELETE, and aborts the whole backup with *"A live probe against audit_log was NOT blocked by: …"*
if either succeeds. A green backup is positive proof the triggers are live.

If (a) shows DDL privileges or (b) shows fewer than two triggers, re-run
`docs/sql/least-privilege.sql` using the exact `${var//…/…}` substitution recipe at its lines
49–55 — **bash parameter expansion, not `sed`**, which eats the backslash, and
`{{DATABASE_ESCAPED}}` substituted before `{{DATABASE}}`.

There is no standalone "was it ever applied?" one-liner in the repo; the verify block lives at
the tail of the same file and still needs its placeholders substituted. The three checks above
are that one-liner, written out.

### 6.3 Check the database's session timezone

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot \
  -e "SELECT @@global.time_zone, @@session.time_zone, NOW(), UTC_TIMESTAMP();"
```

After this deploy expect `+00:00` for both (§3.4's new `--default-time-zone` flag). Before it,
expect `SYSTEM`. `NOW()` and `UTC_TIMESTAMP()` should agree.

This is not cosmetic. `audit_log.created_at` is a MySQL `TIMESTAMP` — stored as UTC, re-rendered
per the **session** zone on every read — and `AuditChain::canonical()` v3 hashes that rendered
string verbatim, deliberately, so that an `APP_TIMEZONE` change can never re-render history. It
was reproduced empirically: an intact 20-row chain, `SET GLOBAL time_zone='+03:00'` against the
same unchanged rows, verification broken at row 1; reverting made it intact again. **Never run
`SET GLOBAL time_zone` against this database.**

### 6.7 The first backup after the slug change

Setting `INSTANCE_SLUG=qch` changes the archive filename from
`endorsement-<Str::slug(APP_NAME)>-…` to `endorsement-qch-…`. The retention sweep's glob is
**anchored per slug** (so `qch` cannot match `qch-2`), which means the old-named archives are no
longer in `--keep`'s window — `BackupRun` counts foreign-slug archives and **warns**, but never
prunes them. Expect that warning on the first run after the change; it is not a fault. Delete the
old-named archives by hand once you are satisfied the new ones restore.

## 7. Rollback, honestly

**There is no clean rollback for this deploy past migration #6.** Everything below is written to
make that concrete rather than to offer a `down()` that half-works.

### 7.1 Before migration #6 has run

Coolify → Deployments → the last good one → Redeploy. Complete and lossless. This is the only
window in which "roll back the code" means anything.

### 7.2 After migration #6 has run

`users.full_name` and `users.position` no longer exist, and the `8886f8d` image reads both — from
`HandleInertiaRequests`, which runs on every page. **Redeploying the old image produces a site
that 500s on every request.** Your options are:

1. **Roll forward.** Fix the defect, push, deploy. For anything short of data corruption this is
   the right answer.
2. **Restore the §1.3 backup and redeploy `8886f8d`.** This discards every clinical write made
   since the backup was taken. It is a decision about patient records, not about software.

`migrate:rollback` is a third option only in the narrow case where the *schema* is the problem and
no new data has been entered. Read §7.3 before considering it.

### 7.3 What `migrate:rollback` actually does here

All 22 run in **one batch**, so a bare `php artisan migrate:rollback` reverses **all 22** in
reverse file order. That order happens to be correct — #6 (`move_name_and_position_off_users`)
unwinds *before* #4 (`create_people_and_link_users`), which is the mandated sequence — and it was
verified clean against real MySQL 8.4 for the identity subset. Use `--step=N` to reverse exactly N
migrations instead (`Migrator::getMigrationsForRollback()`: `--step` counts migrations, not
batches).

It needs `DROP` in addition to the deploy grant, granted for the one operation and revoked
immediately:

```bash
sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "GRANT ALTER, CREATE, REFERENCES, DROP ON \`$DBNAME\`.* TO '$DBUSER'@'%'; FLUSH PRIVILEGES;" && {
  sudo docker exec -u app "$APP" php artisan migrate:rollback --step=1 --force; rc=$?
  sudo docker exec -e MYSQL_PWD="$PW" "$DB" mysql -uroot -e "REVOKE ALTER, CREATE, REFERENCES, DROP ON \`$DBNAME\`.* FROM '$DBUSER'@'%'; FLUSH PRIVILEGES;"
  echo "rollback exit=$rc"
}
```

Per migration, honestly:

| 21 | `create_clinics_and_attendees_tables` | `dropIfExists` ×2 | Every clinic definition and attendee rule, gone. |
| 20 | `create_vacations_table` | `dropIfExists` | Every booked leave row, gone. |

## 9. MySQL-only hazards

The suite is 1,679 tests on SQLite `:memory:`. Production is MySQL 8.4 with
`utf8mb4_unicode_ci` (`config/database.php` line 67) — **not** MySQL 8.4's own default
`utf8mb4_0900_ai_ci`. This section is what that difference hides. Everything below was read; the
three marked **verified here** were reproduced.

### 9.0 What is already fixed, and what the rehearsal did and did not cover

`docs/superpowers/plans/2026-08-15-mysql-production-defects.md` records four defects found by a
real MySQL 8.4 rehearsal, **all fixed and in this tree**: the migration grant
(`ALTER, CREATE, REFERENCES`, `+DROP` for rollback, `INDEX` never needed); the `TEXT` byte
ceiling and the 1.783× encrypted-envelope growth constant; `2026_08_10_120001`'s `down()`
ordering (`dropUnique` before `dropConstrainedForeignId` → `1553`); and WARD's `clinic_owner`.
`docs/superpowers/plans/2026-08-08-p0b-bounded-custom-fields.md` records the fifth: an encrypted
payload must never live in a `json()` column.

**The rehearsal ran the chain as it stood on 2026-08-09** — it did not include
`2026_08_16_120001` or `2026_08_16_120002`, which landed 2026-08-11. Both are plain
`Schema::create` with `constrained()` FKs, the shape the rehearsal already characterised.

**Checked and clean** (recorded so it is not re-derived): no `enum` anywhere; no `json` column
carries a literal default; no composite unique comes near InnoDB's 3072-byte limit (worst is
`people.email` at 1020 B); no NOT NULL column is added to a populated table without a default;
`->change()` is used at exactly one site and restates `nullable()`; no `whereJsonContains`, no
`LIKE`, so no `_`/`%` escaping exposure; NULL ordering agrees on both engines; every `VARCHAR(n)`
is at least as long as its `max:n` rule (MySQL counts characters, the same unit Laravel does — the
byte-vs-character trap is a `TEXT`-only problem); and **foreign-key enforcement is genuinely on in
the test suite** (`config/database.php` line 51 defaults `foreign_key_constraints` true and
`phpunit.xml` does not override it), so the new tables' `restrict`/`cascade`/`nullOnDelete`
semantics *are* exercised. Four `groupBy(` sites, none exposed to `ONLY_FULL_GROUP_BY`.

**The preview/confirm digests are date-safe.** Every `StatePin::of()` caller formats its dates
before hashing (`RotaFill::digest()` via `->format(Calendar::YMD)`, `RotaImport::stateDigest()`,
`DemoDepartment::planDigest()`/`removalDigest()` which carry no dates at all), and both bulk
writers re-sort spans in PHP. Pins will not spuriously refuse on MySQL.

### 9.1 A `date` column round-trips differently — and this codebase records the direction BACKWARDS

**Verified here**, against SQLite in-process, with Laravel's own format:

```
Laravel sends (both engines):  '2026-08-12 00:00:00'   (Grammar::getDateFormat(), not overridden
                                                        by either the MySQL or SQLite grammar)
MySQL DATE column stores:      '2026-08-12'            (the type truncates it)
SQLite stores:                 '2026-08-12 00:00:00'   typeof = text  (no DATE type; NUMERIC
                                                        affinity, non-numeric value → verbatim)

  sqlite> select count(*) from t where d  = '2026-08-12';   -- 0
  sqlite> select count(*) from t where d <= '2026-08-12';   -- 0
```

So **SQLite is the strict engine here and MySQL is the lenient one.** A plain `= 'Y-m-d'`
equality fails on SQLite and *succeeds* on MySQL.

`app/Support/Clinics/ClinicRoster.php` lines 133–136 says the opposite — *"MySQL round-trips such
a column as `'Y-m-d 00:00:00'`, so a plain equality against `'Y-m-d'` never matches on the engine
production runs"* — and `MasterRotaAssignment::booted()` and `Vacation::scopeIntersecting()` both
cite that wording, as do two plan docs.
`app/Http/Controllers/EndorsementController.php` lines 650–654 states it correctly.

**Nothing is broken by this.** The mitigation everywhere is `whereDate()`, which is correct on
both engines, and the real observed failure the code documents (a `firstOrNew(['handover_date' =>
'Y-m-d'])` inserting a duplicate) was a *SQLite* failure. But do not carry the inverted rule into
an operational decision: it implies MySQL will reject something it will in fact silently accept,
which sends a future fix to the wrong place. Correcting those comments is a follow-up, not a
deploy blocker.

### 9.2 `levels.code` is UNIQUE with no case normalisation — one CSV, two outcomes

`levels.code` is `string(20)->unique()` and `Level` carries **no** `code` mutator — deliberately,
and `app/Http/Requests/Admin/LevelRequest.php`'s docblock says so explicitly (*"Unlike
`Unit::code`, `Level::code` carries no write-time mutator"*). `Unit::code` **does** normalise
(`strtoupper(trim(...))`, and `Unit::findByCode()` uppercases the needle), which is exactly the
asymmetry.

`app/Support/Roster/RosterImport.php` line 307 looks a level up with
`Level::query()->where('code', $levelRaw)->first()` on raw CSV text — while line 295 immediately
above it *does* fold case for `Position` via `whereRaw('LOWER(name) = ?')`.

**What this means for the first roster import:** a file containing `r1` **imports cleanly on
production** and is refused with *"unknown level code"* in any SQLite rehearsal. And
`ReferenceSeeder`'s `Level::firstOrNew(['code' => $code])` will *match* an administrator-renamed
differently-cased row on MySQL (no-op) but *miss* it on SQLite (duplicate insert).

```sql
-- Must return no rows. Run after §4.3.
SELECT LOWER(code) AS folded, COUNT(*) FROM levels GROUP BY folded HAVING COUNT(*) > 1;
```

### 9.3 `users.member_name` is case-insensitive on production and case-sensitive in every test

`app/Http/Controllers/Auth/AuthenticatedSessionController.php` line 70 is
`User::where('member_name', $data['member_name'])->first()` with no normalisation on read or
write — while the brute-force throttle key three lines above *is* `Str::lower(...)`ed.

Two consequences:

- **Auth:** on production `AHMED` signs in as `ahmed`. Every login test proves the opposite.
- **Provisioning — this is the one that will surprise you.** `Rule::unique('users','member_name')`
  (`InvitationAcceptController`, `UserManagementController`) will **reject** a new handle that
  differs only in case from an existing one, **including a soft-deleted account's**, which still
  holds the index. An invitation-acceptance flow green in the suite can 422 on production.

```sql
-- Expect 0 (MySQL would already have refused a collision). Worth running anyway, because it
-- is also the check on any historical LegacyImport output.
SELECT LOWER(member_name) AS folded, COUNT(*) FROM users GROUP BY folded HAVING COUNT(*) > 1;
SELECT LOWER(short_name)  AS folded, COUNT(*) FROM people WHERE short_name IS NOT NULL
 GROUP BY folded HAVING COUNT(*) > 1;
```

### 9.4 `people.short_name`, and the two importers that resolve through it

Same collation mechanism, three live call sites:

- **`app/Support/Rota/RotaImport.php` line 983** — `Person::withTrashed()->where('short_name',
  $handle)`. Worse than a plain lookup difference, because the cell key at line 446 folds case
  *only when the person is null*. For a file containing both `ahmed` and `AHMED`: on **MySQL**
  both resolve to one person and become **one** cell whose spans are overlap-checked; on
  **SQLite** one resolves and one does not, producing a second, unresolved cell. Identical bytes,
  two import outcomes.
- **`app/Support/Roster/RosterImport.php` lines 353 and 440/451** — the secondary match key and
  the `crossMatchErrors()` collision pre-flight. Here MySQL is the *stricter* engine: a roster
  file that imports clean against SQLite produces per-line *"short name belongs to a different
  person already on the roster"* refusals on production.

**Practical instruction: do the roster dry-run preview against production, not against a local
rehearsal.** The preview is the deliverable, and it is the only place these two engines agree to
tell you the truth.

### 9.5 Row order on the rota grid and export is not reproducible on MySQL

`App\Support\Rota\RotaGrid` orders people in SQL (`orderBy('people.full_name')`, line 102) and,
in the stale-rows branch only, re-sorts in PHP (`sortBy(...)`, line 128); `usort()` at lines
222–227 relies on PHP's stable sort to preserve ties. On SQLite both orderings are byte order, so
they agree. On MySQL `utf8mb4_unicode_ci` is case- **and accent**-insensitive: `Ahmed Ali` and
`ahmed ali` collate **equal**, as do Arabic alef variants, and MySQL's order among equal keys is
unspecified. So the grid can render in a different order depending on whether stale rows exist,
and the "stable" tie order is not reproducible between page loads.

Same shape in `RotaExport` (SQL `orderBy('starts_on')` then PHP `sortBy(readingOrder)`), whose
stated purpose — *"a diff between two exports of the same year is legible"* — does not hold on
MySQL for two people sharing a `full_name`.

**Watch for:** an export diff that shows spurious moves. Not a correctness bug; do not chase it as
one.

### 9.6 Every range read on the new rota tables uses `whereDate()`, which is non-sargable on MySQL

The new migrations create exactly the indexes these reads want —
`master_rota_assignments(starts_on, ends_on)`, `vacations(starts_on, ends_on)`,
`periods(starts_on, ends_on)`, `handovers(unit_id, handover_date)` — and **47** `whereDate()` /
`orWhereDate()` call sites across sixteen files wrap the column in a function, because of §9.1's
rule. MySQL compiles `whereDate()` to
`date(col) op ?`, and a wrapped column generally cannot use the index.

With 1,679 in-memory tests over a handful of rows this is structurally invisible. **Verify with
`EXPLAIN` once real data exists** — the rota grid for a full academic year, and the handover day
index:

```sql
EXPLAIN SELECT * FROM master_rota_assignments
 WHERE DATE(starts_on) <= '2027-06-30' AND DATE(ends_on) >= '2026-07-01';
EXPLAIN SELECT handover_date, COUNT(*) FROM handovers
 WHERE unit_id = 1 AND DATE(handover_date) >= '2026-07-01' GROUP BY handover_date;
```

`type: ALL` means a full scan. The fix is a half-open range (`>= $from AND < $toPlusOne`), which
is index-friendly **and correct on both engines** given §9.1's storage facts. Do not attempt it
during this deploy.

### 9.7 Locks that are no-ops in every test

`SQLiteGrammar::compileLock()` returns `''`, so `lockForUpdate()` is compiled away in all 1,679
tests. Four call sites, all of which depend on it:

| Site | What the lock is holding |
|---|---|
| `app/Models/AuditLog.php:64` | The chain tail. **The only thing stopping two concurrent audited actions reading the same `prev_hash` and forking the chain.** It is also a descending index scan `FOR UPDATE` on an ever-growing table taken by *every* audited write — on MySQL it serialises writes; in tests it costs nothing. |
| `app/Http/Controllers/Auth/InvitationAcceptController.php:88` | Two people opening one invitation link at once |
| `…:121` | The person row while the account is claimed |
| `app/Support/Demo/DemoDepartment.php:724` | Ruling 59 — the pre-flight inside the deleting transaction. Nine of nineteen inbound keys are `SET NULL`, so the unguarded shape **succeeds** and leaves a sign-off naming nobody. Already asserted at source level. |

`DemoDepartment`'s loop is also the app's **only multi-table lock acquisition** (up to nine tables,
in ledger order) and can contend with `AuditLog`'s chain-tail lock. It is the one place a `1213`
deadlock or `1205` lock-wait timeout can appear. Low reachability — one demo, admin-only — but
nothing in this suite can produce either.

```sql
-- After the first week. A forked chain shows up as a shared prev_hash.
SELECT prev_hash, COUNT(*) FROM audit_log WHERE prev_hash IS NOT NULL
 GROUP BY prev_hash HAVING COUNT(*) > 1;
```

### 9.8 Lower-priority, recorded so they are not rediscovered

- **The collation is PAD SPACE and that is not MySQL 8.4's default.** `utf8mb4_unicode_ci` treats
  `'PICU'` and `'PICU '` as equal for comparison *and* for UNIQUE; `utf8mb4_0900_ai_ci` (the
  server default) does not. Mitigated in practice — Laravel's global `TrimStrings` is not removed
  and both CSV readers trim every value — so the two never meet. Recorded because the choice is
  deliberate and divergent, and because it is the same property that makes §9.5 accent-insensitive.
- **`App\Support\UnitMerge`'s field-key pre-flight** compares keys with an exact PHP string match
  while the constraint it guards, `unique(unit_id, key)`, folds case on MySQL. Its comment claims
  a database guarantee that is not there. Unreachable today — `UnitFieldDefinition::booted()`
  enforces `^[a-z][a-z0-9_]{0,63}$` on save — so only a raw SQL insert could produce a
  `Weight`/`weight` pair.
- **`LegacyImport` has never run against MySQL either.** It matches and upserts on
  `member_name`; two legacy rows differing only in case **collapse into one `users` row** on
  MySQL and stay two on SQLite. Its own reconciliation counts will surface it — treat a mismatch
  there as this, not as a new bug. Only relevant if the owner ever changes their mind about the
  import (`docs/RUNBOOK-IMPORT.md`).
- **`handovers.extra_fields` is still `TEXT`** and was deliberately not widened by #17. It is
  bounded at 32,000 pre-encryption bytes by `EncryptedJson::MAX_BYTES`, which at the measured
  1.783× envelope growth is ~57,056 bytes against `TEXT`'s 65,535 — safe, but a **13% margin**.
  If that growth constant is ever re-measured higher, this is the next column to overflow.
- **Non-atomic DDL is not confined to the one migration the standing runbook names.** Every
  migration that emits more than one statement has the same partial-application exposure:
  #7 (4 adds + 4 constraints + 4 updates), #16 (three separate `Schema::table()` calls),
  #19/#20 (create + 3–4 FKs each), #21 (**two** tables + 5 FKs), and #1/#10/#13 (multi-column
  adds *plus* a data backfill in one `up()`). `docs/RUNBOOK-DEPLOY.md`'s "recovery before you
  retry" procedure applies to **all** of them, not just to `2026_08_09_120001`.
