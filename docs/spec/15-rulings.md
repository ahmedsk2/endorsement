## P1c-2 rulings (2026-08-10)

| # | Decision | Ruling |
|---|---|---|
| 30 | Unbinding an account snapshots the signer's name first | `App\Support\AccountUnbind` writes `handover_signoffs.signed_off_by_name` for that account's un-snapshotted rows **before** clearing `users.person_id`, inside the same transaction. The chain that makes it necessary: `signed_off_by_name` was added additive-and-nullable on 2026-07-27 and deliberately **not** backfilled, the sheet reads the snapshot and falls back to `signedOffBy?->full_name`, and that accessor resolves through `users.person_id` → `people.full_name` — so for every handover signed before that date, unbinding blanks "signed off by" on medico-legal evidence. That is exactly the failure the freeze migration exists to prevent, reached through a different door, and under the 2026-07-27 signature-by-proxy ruling (`docs/OPEN-DECISIONS.md`) that line is the whole attestation wherever a signature was withheld. The update writes a **currently-null** column with the value the sheet already renders; `whereNull` is what keeps it a snapshot rather than a rewrite. Both alternatives were worse: refusing to unbind blocks turnover permanently (the thing AC-03 exists to enable), and unbinding without it destroys attribution silently. The count goes in the audit detail; the name never does. Watched failing first — the rendered signer moved to `null` on an implementation with the snapshot omitted |
| 31 | No passwordless sign-in | Munawib AC-01's *"email link; password optional"* is read as: the **invitation** is the email link and the claim screen sets the password. **AC-01 was already satisfied end to end by P0c and P1c-2 implemented no part of it.** There is no magic-link login, no "email me a code to sign in", no `login_tokens` table, and none is coming — the only email link that authenticates anything authenticates a *claim*, once, not a session. Recorded so a future reader does not reopen *"password optional"* as an unbuilt requirement (owner decision 1, 2026-08-10) |
| 32 | Roles are not restored to a returning colleague | Capability grants stay keyed to the **account** (`user_capabilities.user_id`); AC-04's per-person granting is a second surface on `App\Support\CapabilityGrant`, gated `access.manage` and never `people.manage`. A person who leaves and later returns does so on a **new account** and an administrator re-grants their roles. There is deliberately no rebind action: auto-restoring on re-bind reattaches a departed administrator's grants to whoever claims that identity next, reviewed by nobody. The sentence appears on the screen itself, not only here (owner decision 2, 2026-08-10) |
| 33 | Resend rotates the token | A resend mints a **new** invitation and marks the superseded row revoked; it never re-mails the existing token. Re-mailing would extend the life of a credential that may already be in the wrong hands, make revoking the first link meaningless (the "revoked" one and the "new" one being the same secret), and break the property the system already had — at most one live link per person. The superseded row is **kept**, never deleted: who invited whom, how many times, is the history AC-03 preserves and the only evidence if a link turns up where it should not. `App\Support\Invitations\InvitationIssue` is the one writer; the live set is matched `person_id = X OR member_email = Y`, because an address-only match leaves a live link to the old mailbox the moment somebody's address is corrected |

## P1c-2 adversarial-review rulings (2026-08-11)

| # | Decision | Ruling |
|---|---|---|
| 34 | What an invitation is authorized against | The **bound person's** `people.position`, never `invitations.position` — asserted once, at the one writer (`InvitationIssue::issue()`), beside the supersede loop and before the transaction opens. `InvitationAcceptController` takes the `person_id !== null` branch for every row this system mints and that branch does **not** write `position` (deliberately: `people.position` has one writer, and an invitee must not re-rank the roster row they are claiming), so a redeemed account resolves its capabilities from the ROSTER while all four endpoints checked a column nothing downstream consults. The two diverge with **no misuse at any step**: an administrator invites a new joiner at 4, later corrects that roster row to 0 — a correction that must not reach into `invitations`, and does not — and the live invitation still reads 4, which a Chief Resident may target. Resend, bulk resend and (through `Person::matchByEmail()`) invite would each have handed them a link that mints an Administrator; AC-03's `AccountUnbind` newly manufactures the roster-only position-0 precondition. `InvitationStatus::mayInvite()` already gated the OFFER on `people.position`, so this is D9 restored to the write side. Do **not** close the asymmetry by writing `position` at redemption |
| 35 | Who may place somebody at position 0 | An actor holding **`users.manage`** — gated in `PositionChange::write()`, the single definition all three writers pass through, never in `PersonRequest` alone (which `App\Support\Roster\RosterImport` bypasses by calling `applyWithoutAudit()`, resolving its position column by NAME against `positions` from a `cap:people.manage` route). **This falsifies AC-04's stated premise**: Decision F reasoned that hanging a role control off the roster gate *would* create an escalation path, but position 0 carries `access.manage` by seeded role default and `AccessControl::resolve()` reads `people.position`, so `people.manage` was already one. It is the **TRANSITION** that is gated, not the value — a `people.manage` holder may still edit a sitting Administrator's roster row, because the edit form submits the position it was rendered with; a CREATE is a placement, distinguished by `wasRecentlyCreated`. It throws rather than auditing: a refusal written inside `PersonController`'s or `RosterImport`'s transaction rolls back with it. **This changes People-screen behaviour** — `grantable_positions` (`PositionChange::grantableBy()`, the same definition the refusal comes from) is what the two role `<select>`s offer, plus whatever the row already holds |
| 36 | Baseline authorization on a bulk resend | `BulkResend::positionsToAuthorize()` returns the **union** of every selected person's `people.position` and their live invitations' positions, and is therefore **never empty for a non-empty selection**. The invitation half alone returned `[]` for a cohort that had all claimed or was never invited, and `bulkPreview()`/`bulkResend()` sit in an **`auth`-only** route group — invitations being this codebase's one deliberate exception to a `cap:` middleware, the rule being two-tier and position-dependent. That exception is only sound while the in-controller pass is guaranteed to assert something; it was not, and any authenticated account received the plan: per person, their invitation state, invitation id and whether they hold an account |
| 37 | One definition of the superseded set | `InvitationIssue::supersededBy()` — used by the writer to know what to revoke and by `positionsToAuthorize()` to know what to authorize first. The two were separate queries and diverged both ways: the pass matched `whereIn('person_id', …)` while the writer matches `person_id = ? OR member_email = ?`, so an invitation reached only along the ADDRESS axis was never pre-authorized and the writer's own `assertMayTarget()` fired from **inside** `BulkResend::commit()`'s transaction — the `user_scope_denied` row rolling back with it, which is P1c-1 finding 12 reached through a different door; and the pass had no expiry filter while the writer requires `expires_at > now()`, so a merely aged-out higher-position row refused a batch the operator was entitled to run. Set-wise and one query, because a cohort of fifty must not cost fifty |
| 38 | What the Access Control detail panel may reach | An account with a **person link**, and nothing else — `whereNotNull('person_id')` in `selectedUser()`, the same set `index()`'s picker already produces with its inner join on `people`, stated as one predicate on both sides so the list and the detail panel cannot disagree about which accounts exist. Not cosmetic: `full_name` and `position` are read-through accessors, so both answer null once `AccountUnbind` has cleared the link, and the projection casts `(int) $user->position` — where `(int) null` is **0, the Administrator role id**, which `AccessControl.vue` renders as "Administrator" beside the login name the panel falls back to. Every other read of this link fails toward a blank; this one failed toward the top of the ladder, on the one screen whose subject is privilege. The refusal is a `null` return, not a throw — already this method's answer for an unknown or array-shaped `user_id`, so the page renders its existing no-selection state and no Vue change describes a new refusal (review F5, 2026-08-11) |
| 39 | Correcting an unbound account's profile | **Refused, not half-applied.** `UserManagementController::updateProfile()` writes `member_name` on `users` and `full_name`/`member_email` through `$user->person?->update(...)`, which on an unbound account is a no-op raising nothing — two of three submitted corrections evaporated, a `user_profile_update` audit row was appended, and the screen flashed "Account details updated." Its sibling `setPosition()` already refuses an unbound account by name; this is the same refusal on the same console. Found by the fifth-path search F5 asked for, and the only site in that survey that is a WRITE — the rest are blanks (`invited_by` renders "—", `PersonPresenter::history()`'s `by`, `printed_by`) or are unreachable, an unbound account being inactive by construction with no rebind action and no reactivation (review F5, 2026-08-11) |
| 40 | Rate-limiting the endpoints that send | **Every endpoint that reaches the mailer carries a `throttle:`**, derived from the router rather than listed by hand — `MailSendingRoutesAreThrottledTest` walks each route's handler and follows **one level of same-class call**, because `InvitationController::store()` contains no `Mail::` at all and ends in `$this->deliver(...)`. A handler-body scan alone would have been green on the defect it exists to catch; a whole-file scan would have named `bulkPreview()` and `revoke()`, which send nothing, and bought an allow-list to excuse them. `admin.invitations.store` and `admin.invitations.resend` shipped with no bound at all — not even the `throttle:clinical` the access-control group carries — while `bulk-resend`'s comment claimed six a minute matched "the only other endpoint in this application that sends on a button press", naming `settings.test-email` and missing the two three lines away. Six is deliberately tight for a hand-driven control: fifty people at once is what `bulk-resend` is for and counts as ONE press. **The bucket is per OPERATOR, not per route** — Laravel keys an authenticated request's signature on the user id alone — so all three sending endpoints share one allowance, which is the right semantics (the relay is what is being rationed) and is asserted rather than assumed (review F6, 2026-08-11) |
| 41 | Where a resend's refusals land | **One key, `invitation`, for all four**, because Admin → People renders exactly one and that is where the per-person Resend button lives. The odd one out was keyed `member_email` for a purely mechanical reason: a Validator names its errors after the field it was handed, and the field `Person::accountEmailRule()` is normally handed is the invite form's address input — so pressing Resend against a since-claimed address flashed nothing at all. The **key** moves and the **predicate** does not: re-typing `hasAccount()` here to obtain a different error key is the drift D9 exists to prevent. Its test asserts the render site too, because without that half a template that stopped reading `errors.invitation` would take all four silent together and leave the four refusal assertions green (review F7, 2026-08-11) |
| 42 | What a single-writer guard scans, and for what shapes | **`tests/` is out; `database/` is IN, factories and seeders included** — the code always did this and three docblocks claimed otherwise. A factory writing the column directly IS a second writer of the guarded shape, merely one whose blast radius stops at the suite, so it is **named in the allow-list** (as `PersonLevelsHaveOneWriterTest` and `RotaWritersAreSingularTest` already do) rather than exempted by directory, which would exempt every future factory invisibly. It matters most for `user_capabilities`, whose guard also covers `AccessControlSeeder` — production code. The needle sets cover **three shapes a `Model::create(`/`DB::table(`/array-literal set misses**: property assignment then `->save()`, the four relation-write spellings beside `create`, and `find()` then `destroy()`/`delete()`. Every needle is proved by planting a writer of exactly its shape and watching the guard name the file, with a negative control proving a plain READ still passes — which is what keeps the `= ` trailing space on a property needle load-bearing. A needle whose cost exceeds its reach is **withdrawn on measurement, not taste**: `User::find(` named three legitimate auth readers plus one file that merely quotes the expression in a comment. The residual gap — `$model->delete()` on an already-bound instance, invisible to any substring — is stated in each docblock rather than implied away (review F8/F9, 2026-08-11) |
| 43 | What a "two doors agree" test must do | **Open both doors, and compare the answers as values.** `PersonRolesTest::test_the_people_panel_refuses_exactly_what_the_access_control_screen_refuses` posted to `/admin/access-control/person` twice, so the screen it claimed parity with was never exercised and a refusal added to one door alone would have left it green — the declared-and-never-exercised shape finding 4 recorded elsewhere, which reads in review exactly like something enforced. Each case now goes through both endpoints and the two outcomes are compared as a projection — status, the `overrides`-shaped error keys, and the rows each actually wrote — rather than asserted separately against a hand-written expectation each side could drift from. A case for a **well-formed grant** is part of the set, because two doors that both refuse everything also "agree". Proved by planting three divergences in one door and watching each go red, one per part of the projection (review F10, 2026-08-11) |
