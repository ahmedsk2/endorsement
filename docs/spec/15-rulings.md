| # | Decision | Ruling |

| 44 | `access.manage` must always have an active holder | Enforced in **`App\Support\CapabilityGrant::applyForUser()`** — the one writer both override surfaces delegate to — and nowhere else. `AccessControlController::assertNoSelfLockout()` only ever guarded the **role matrix** (position 0 may not give up the capability via `updateRole()`/`updateRoles()`) and never ran on the per-user path at all, so an administrator could `PUT /admin/access-control/user` with `overrides => [<access.manage> => 'deny']` against **their own account**, receive a 302, and leave `AccessControl::holdersOf('access.manage')` answering nobody: Admin → Access Control unreachable, access control uneditable, no recovery but the database. AC-04's People panel inherited it exactly, one writer being the reason. The guard is **asked, not derived**: the rows are written, then `holdersOf()` — already the definition of "who effectively holds this", uncached by design — is consulted **inside** the transaction, and an empty answer throws, which unwinds the write and (the audit being written after the commit) leaves no row claiming it happened. Predicting the answer from the submitted map would be a fourth copy of the resolution rules and would get the hazard wrong: **the danger is not the word `deny`**. Clearing a per-user *grant* that was somebody's only claim strips the capability just as completely, and an omitted key is how this API spells that. Phrased over the **holder set**, not the actor: today every actor reaching the writer is themselves a holder (they passed `cap:access.manage` and `EnsureAccountActive`), so "nobody is left" and "I am not left" coincide — but they coincide only because `capabilitiesFor()` (which consults neither `users.active` nor the person link) and `holdersOf()` (which consults both) agree, and nothing enforces that agreement, so A-denying-B stays covered for the same one query |

| 48 | A validation rule is asked only of the list its MODE reads | `ClinicAttendeesRequest` applies `ClinicPickers::levelRule()` to `level_ids.*` only when `mode === levels` and `personRule()` to `person_ids.*` only when `mode === named`. Applying both unconditionally read as belt-and-braces and was a **permanent lockout**: `attendeeRows()` builds from one list and discards the other, so the discarded list was refusing requests over ids that could reach neither the writer, the database, nor any element on the screen. Retire a training level from Admin → Structure → Levels, or deactivate a colleague via `PersonStatus::apply()` — plain first-class administrative acts, and a soft delete freezes it identically — and every later save of that clinic's rule was refused under `level_ids.N` / `person_ids.N`, keys **the clinics screen renders no element for**: `onSuccess` never fired, the panel stayed open, nothing was reported. **Switching to `rotators` did not escape it**, which is what made it permanent rather than transient — the one mode that needs no rules at all was refused by the same unconditional pair, so no reachable state could repair the clinic. **Both halves are the fix and neither is sufficient.** Client: `startAttendees()` seeded the form with the clinic's WHOLE stored id list, so an id with no checkbox went back on every save and no control could remove it; it now seeds the intersection with what the pickers offer, which is also what makes the panel's own banner (*"No longer offered, and saving will drop them"*) true for the first time — it previously promised a drop that nothing performed. Server: the narrowing above, which is what stops a hand-edited or stale payload doing the same thing. **D9 is unmoved** — the offer and the write side are still ONE predicate per field, and the mode that READS a list still refuses every id that list never offered, asserted at `active = false`, at `deleted_at` and on a retired level. What changed is which list is asked, not what the asking accepts. The client half is asserted on the **submitted payload**, not the DOM: a form holding `[5, 99]` and one holding `[5]` render byte-identical markup when 99 has no checkbox, so every visible surface was correct while the request body was not |
| 49 | Where a refusal lands, and why there is no source-level guard for it | **The pairing is asserted behaviourally, in two halves, at each refusal — the flash key in PHPUnit and the render site in Vitest** (ruling 41's discipline, now applied to `ClinicController::setActive()`, the only member of the Units/Levels/Holidays/Clinics `setActive()` family that can refuse at all; the other three cannot fail). A clinic cannot be revived onto a unit that has since been retired or stopped owning clinics, and that refusal was flashed under `active` while nothing on the screen read it — so Restart did nothing visible whatever. This is the **third instance of the shape in two slices** (ruling 41's single resend under `member_email`; ruling 48's attendee lists), so a source-level guard — *every validation key a controller can flash must be rendered by some screen* — was designed and **MEASURED, then rejected**. Three reasons, in order of decisiveness: (1) **it is green on the defect it would be built for.** `errors.person_ids` IS rendered — by Admin → People's bulk-resend panel — so ruling 48's `person_ids.N` refusal satisfies "rendered by SOME screen" through an unrelated form on an unrelated page. (2) **The sound version is not a static property.** `back()` picks its screen from the referrer at runtime; the question is per-SCREEN and a substring scan has no controller→route→Inertia-component→form edge to follow. (3) **Cost.** Extending it to FormRequest rule keys — necessary, since ruling 48's keys come from a rules array and not from `withErrors` — puts ~70 keys in scope against ~55 rendered, and the Clinics screen alone deliberately renders none of `location`, `note`, `level_ids`, `person_ids`, `active`. A guard whose allow-list starts at dozens of entries and cannot see the bug is decoration. Recorded as a measurement so the next reviewer does not re-derive it |
| 50 | A single-writer guard must needle `$model->update([...])` | **The house idiom, and `ClinicWritersAreSingularTest` shipped blind to it.** Proved rather than reasoned: a planted file rewriting `weekday`, `session`, `attendee_mode`, `clinic_id`, `name` and `active` across BOTH clinic tables through nothing but `update([...])` left the guard **green** — an entire endpoint could have bypassed `ClinicWriter` with the build passing. It is not hypothetical for this shape: `UnitController`, `LevelController` and `HolidayController` each write their own `setActive()` exactly that way, so it is what a fourth controller written beside them reaches for. **Two needle families, kept because they fail for different reasons:** column-qualified (`->update(['weekday'` …, catching the idiom whatever the variable is called) and variable-qualified (`$clinic->update(`, `$attendee->update(`, catching it whatever the COLUMN is — the only reach this guard has over `name`, `active`, `location`, `note` and `unit_id`, each of which is another table's column too). Observed on the plant: the column form matches only the array's FIRST key, so `update(['weekday' => 3, 'session' => 'PM'])` fires one needle and not the other, and the variable form is what named the file for the `name`/`active` write. **Measured before adding, per ruling 42:** all twelve new needles had ZERO pre-existing matches, so no allow-list entry was bought. **`->update(['active'` was written, measured and WITHDRAWN** — it names six files, every one writing a different table's `active` column, and two of them (`UnitController`, `UnitMerge`) are the files most likely to grow a real clinic writer; `UnitMerge` especially, since design §14 item 23 records that it re-points four unit-owned tables and not `clinics.unit_id`. An allow-list entry there would blind this guard precisely where the next offender arrives. `$row->update(` was rejected for the opposite reason: fragile toward FALSE positives, `$row` being a general-purpose local. **The siblings were probed, not read** — one `$model->update([...])` per guarded table, planted and run: `RotaWritersAreSingularTest` (green — `master_rota_assignments`, `vacations`) and `PersonLevelsHaveOneWriterTest` (green — `person_levels`, which is *literally* how `LevelAssignment` writes `effective_to` twice) **share the hole**; `InvitationWritersAreSingularTest`, `AccountLinkHasOneWriterTest` and `CapabilityWritersAreSingularTest` do **not**, each closing it incidentally — the first two through bare array-key needles that reach inside the update literal (`'revoked_at' =>`, `'effect' =>`), `AccountLinkHasOneWriterTest` through an explicit `->update(['person_id'`. The two open ones are left open here: they guard P1d's and P1c's tables, the same scope line design §14 item 23 draws |
