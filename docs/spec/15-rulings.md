| # | Decision | Ruling |

| 44 | `access.manage` must always have an active holder | Enforced in **`App\Support\CapabilityGrant::applyForUser()`** — the one writer both override surfaces delegate to — and nowhere else. `AccessControlController::assertNoSelfLockout()` only ever guarded the **role matrix** (position 0 may not give up the capability via `updateRole()`/`updateRoles()`) and never ran on the per-user path at all, so an administrator could `PUT /admin/access-control/user` with `overrides => [<access.manage> => 'deny']` against **their own account**, receive a 302, and leave `AccessControl::holdersOf('access.manage')` answering nobody: Admin → Access Control unreachable, access control uneditable, no recovery but the database. AC-04's People panel inherited it exactly, one writer being the reason. The guard is **asked, not derived**: the rows are written, then `holdersOf()` — already the definition of "who effectively holds this", uncached by design — is consulted **inside** the transaction, and an empty answer throws, which unwinds the write and (the audit being written after the commit) leaves no row claiming it happened. Predicting the answer from the submitted map would be a fourth copy of the resolution rules and would get the hazard wrong: **the danger is not the word `deny`**. Clearing a per-user *grant* that was somebody's only claim strips the capability just as completely, and an omitted key is how this API spells that. Phrased over the **holder set**, not the actor: today every actor reaching the writer is themselves a holder (they passed `cap:access.manage` and `EnsureAccountActive`), so "nobody is left" and "I am not left" coincide — but they coincide only because `capabilitiesFor()` (which consults neither `users.active` nor the person link) and `holdersOf()` (which consults both) agree, and nothing enforces that agreement, so A-denying-B stays covered for the same one query |
